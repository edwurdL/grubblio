# Grubblio (prototype)

Guess the dish from its ingredients. You start with three ingredients. Each wrong guess reveals another ingredient. You get 9 guesses. When the game ends, it shows the answer with a photo.

Each guess is compared with the answer column by column, in the style of Royaledle:

| Column | Green | Yellow | Red |
|---|---|---|---|
| Type | same family (Pizza) | related family (Flatbread, Sandwich…; Cake, Pudding…) | otherwise |
| Origin | same country | same region (e.g. Europe) | otherwise |
| Diet | same | one step on Vegan → Vegetarian → Pescatarian → Omnivore | otherwise |
| Palate | identical set | some overlap | none |
| Course | same | both light (starter/side/snack) | otherwise |
| Method | same | same style (dry heat / oil / wet heat) | otherwise |
| Spice | same | off by one (▲▼ arrows show which way) | further |
| Ingredients | the right dish | ≥25% of the answer's ingredients shared | fewer |

A **closeness** score (0–100%) combines all the columns, so players can tell when they're close.

There is no autocomplete. On submit, an exact name or alias ("Chicken Parm", "Lasagne") is guessed straight away. Anything close gets a **"Did you mean …?"** prompt instead. Matching uses only dish names and their `aliases` (also-known-as names). What you type has to read as a whole name, with small typos allowed: "bufalo chiken pizza" → Buffalo Chicken Pizza, and "pinapple pizza" → Hawaiian Pizza via its "Pineapple Pizza" alias. A name of three or more words can be missing one word ("buffalo chicken"). Ingredients and single fragments ("pineapple", "chicken") match nothing, so players can't search their way to the answer. To accept another way of naming a dish, add an alias in `server/dishes.ts`.

## Game modes

- **Daily dish** is the default. Everyone gets the same answer on the same local date, as in Wordle ([Daily dish](#daily-dish) below). Progress is kept per date, so playing Rush hour never loses it, and the **Daily dish** button brings it back.
- **Rush hour** deals a random dish. Once you've made a guess, you have to finish that order before another is dealt. Clicking **Rush hour** reopens it with "Finish this order before taking a new one." in the hint line. Before your first guess you can still swap the dish. For signed-in players this rule follows the account across devices: the server hands back the oldest unfinished Rush hour first.

Share results include the mode, and the date for a Daily dish: `Grubblio · Daily dish · Nov 5 · 3/9`.

There are about 430 dishes, in [server/dishes.ts](server/dishes.ts).

## Run it

```bash
npm install
npm run dev          # http://localhost:5173 — site + API Worker in one process
```

The API is a Cloudflare Worker ([server/index.ts](server/index.ts)). `npm run dev` runs it locally inside Vite via `@cloudflare/vite-plugin`, so no Cloudflare account is needed for development. Before starting, it applies the database migrations to a local copy in `.wrangler/` (`npm run db:local`).

Production-style build: `npm run preview` builds, then serves the built site and Worker locally.

In local dev, sign-up and password-reset codes are printed in the `npm run dev` terminal instead of being emailed (look for `[dev] Grubblio sign-in code`).

## Database (Cloudflare D1)

One D1 database, `grubblio` (binding `DB` in [wrangler.jsonc](wrangler.jsonc)), holds everything that isn't code. Dishes themselves are code, not data: they ship with each deploy.

| Table | What it holds | Written by |
|---|---|---|
| `puzzles` | The Daily dish answer for each date: `date` (YYYY-MM-DD) → `dish_id` | The Worker on each date's first request; `npm run schedule` for hand-picks |
| `user`, `session`, `account`, `verification`, `rateLimit` | Accounts: users, login sessions, sign-in methods (`providerId = 'credential'` holds the hashed password), hashed login codes, and per-IP rate-limit counters | Better Auth ([server/auth.ts](server/auth.ts)) |
| `plays` | One row per game a signed-in player has guessed in: mode (`daily`/`rush`), answer, guesses (JSON), status, timestamps | `POST /api/state` ([server/plays.ts](server/plays.ts)) |
| `d1_migrations` | Which migration files have been applied | Wrangler |

The schema lives in [migrations/](migrations/), applied in order:

- `0001_create_puzzles.sql`: `puzzles`. Its header comment predates self-picking answers; the table itself is unchanged.
- `0002_auth.sql`: Better Auth's tables, generated by `npm run auth:schema`.
- `0003_plays.sql`: `plays`, keyed by `(user_id, puzzle_id)`.

Deleting a user deletes their sessions, sign-in methods and `plays` rows too (`ON DELETE CASCADE`).

Working with it:

```bash
npm run db:local                                              # apply migrations locally (runs before npm run dev)
npx wrangler d1 migrations apply grubblio --remote            # apply to production (npm run deploy does this)
npx wrangler d1 migrations list grubblio --remote             # see what's applied
npx wrangler d1 execute grubblio --remote --command "SELECT count(*) FROM user"
```

To change the schema, add the next numbered file to `migrations/` instead of editing an applied one. After upgrading `better-auth` or changing its settings, run `npm run auth:schema`. If it prints SQL, save it as the next migration.

Usage is far inside the free plan (5 million rows read and 100,000 written a day). Lookups are by primary key, each Worker instance caches each date's answer, and history writes only happen when a signed-in game gains a guess. On the free plan, going over the daily limit makes queries fail until midnight UTC rather than costing money.

## Daily dish

A puzzle's id is its date in the player's local time, as in Wordle. The answers are kept in D1, out of the repo, so nobody can read upcoming answers on GitHub. Past dates stay playable. The API refuses a date that hasn't started in any time zone yet. Without that check, anyone could replay nine wrong guesses on tomorrow's puzzle and see its answer early.

**Each day's answer picks itself.** The first request for a date with no answer yet picks a random dish and stores it, so every later player gets the same one ([server/daily.ts](server/daily.ts)). Dishes that have never been an answer come first. Once every dish has had a turn, a dish can't come back within about seven months (half the dish count, in days). A newly added dish is picked soon after it's deployed. There's nothing to top up or schedule. Answers are only picked for dates that are "today" somewhere, so an old date with no answer stays empty.

To choose answers yourself, use [scripts/schedule.ts](scripts/schedule.ts). It prints dates, never answers:

```bash
npm run schedule -- --remote --set 2026-12-25=gingerbread   # hand-pick a date (repeatable)
npm run schedule -- --remote --days 30                      # pre-pick the next 30 days now
```

Leave out `--remote` to change the local dev database instead. `--set` replaces a date's dish, but only for dates that haven't started anywhere yet. Deploy a new dish before you hand-pick it, or that day's puzzle will name a dish the live site doesn't know.

To try a specific answer locally, change today's row directly (`--set` won't touch a date that has started):
`npx wrangler d1 execute grubblio --local --command "UPDATE puzzles SET dish_id = 'pad-thai' WHERE date = '2026-11-05'"`.

Don't rename or delete a dish id that's already in `puzzles`: that day's Daily dish would stop loading.

## Accounts

Players can make an account to keep their game history, split into **Daily dish** (with current and best streaks) and **Rush hour**, under **My games** in the header. Playing doesn't need one. Accounts use [Better Auth](https://better-auth.com) inside the Worker ([server/auth.ts](server/auth.ts)).

- **Sign up:** name + email → we email a 6-digit code → the account is created only when the code is entered → the player picks a password. Better Auth's plain email-and-password sign-up is switched off, because it would create the account before the email is proven.
- **Sign in** with email + password. **Forgot password** emails a code that sets a new one.
- **History:** every guess a signed-in player makes records that game. A recorded game can only gain guesses, and a won or lost game never changes, so a loss can't be overwritten after seeing the answer. On sign-in, games already played on that device are saved to the account too. Answers are shown only for finished games.
- **Limits:** code emails and sign-in attempts are rate-limited per IP, counted in D1. Codes expire after 10 minutes and allow 5 tries.

Anonymous visitors never call the account API: the page only asks "who am I?" if this browser has signed in before.

### Setting up the code emails (Resend)

Codes are sent with [Resend](https://resend.com) ([server/email.ts](server/email.ts)). Its free plan (about 3,000 emails a month, 100 a day; check their pricing page) is plenty to start.

1. Sign up at resend.com, then go to **Domains → Add domain** and enter `grubbl.io`.
2. Add the DNS records Resend lists in **Cloudflare → DNS** for grubbl.io. For grubbl.io these are a DKIM `TXT` at `resend._domainkey`, and two `CNAME`s for sending, `send` and `rsend`. Set the CNAMEs to **DNS only** (grey cloud); proxied records fail verification.
3. Add the optional DMARC record too: `TXT` named `_dmarc` with value `v=DMARC1; p=none;`. It improves inbox delivery.
4. Click **Verify** in Resend and wait for the domain to show *Verified* (usually minutes).
5. **API keys → Create API key** with *Sending access*, limited to grubbl.io. Then store it and an auth secret in the Worker:
   ```bash
   npx wrangler secret put RESEND_API_KEY      # paste the key (starts with re_)
   npx wrangler secret put BETTER_AUTH_SECRET  # paste the output of: openssl rand -base64 32
   ```
6. Emails come from `EMAIL_FROM` in [wrangler.jsonc](wrangler.jsonc) (`Grubblio <login@grubbl.io>`). No mailbox is needed for that address.

The Worker won't serve sign-in without `BETTER_AUTH_SECRET` in production; anonymous play still works. Keep the secret the same once live, because changing it signs everyone out. To test real emails locally, put `RESEND_API_KEY=…` in `.dev.vars`.

## Photos and sounds

Photos: `npm run fetch-images` downloads a photo for each dish that has none and saves its credit in `assets/dishes/credits.json`. The result card shows the credit. Sources, best first:

- **Pixabay** (or Pexels), when `PIXABAY_API_KEY` (or `PEXELS_API_KEY`) is set. Copy `.env.example` to `.env` and add the key; both are free.
- **Wikimedia Commons**, needing no key. Use `--source commons` to fill the dishes Pixabay found nothing for.

A dish only takes a photo whose description names it; otherwise it keeps its current photo, or its emoji if it has none. In [scripts/fetch-images.ts](scripts/fetch-images.ts), `QUERY` gives better search terms for some dishes, and `REJECT` lists photos found wrong by eye so they're never picked again. To replace a photo, add its page URL to `REJECT`, delete the file and its `credits.json` entry, and run the script for that dish id. Commons matches by file name and is looser than Pixabay, so check new Commons photos by eye. A few dishes (Hush Puppies, Tater Tots, Corned Beef Hash, Jamaican Beef Patty) currently have no photo and show their emoji.

```bash
npm run fetch-images                              # fill in dishes with no photo
npm run fetch-images -- --source commons          # same, from Wikimedia Commons
npm run fetch-images -- --force pad-thai          # look again for these ids
npm run fetch-images -- --restore                 # re-download the recorded Pixabay/Pexels photos
```

Pixabay and Pexels photos are **not committed**: their licences don't allow redistributing the raw files, so `assets/dishes/.gitignore` (regenerated on every run) lists them, while `credits.json` stays in git. After cloning, run `npm run fetch-images -- --restore` with `PIXABAY_API_KEY` set to download exactly the recorded photos again. Wikimedia Commons photos are committed, with their credits.

## Deploy (Cloudflare Workers)

One Worker serves everything: the built site and dish photos as static assets, and `/api/*` from [server/index.ts](server/index.ts). It's configured in [wrangler.jsonc](wrangler.jsonc), including the `grubbl.io` and `www.grubbl.io` custom domains. Cloudflare creates their DNS records and certificates on the first deploy.

**From your machine:** `npx wrangler login`, then `npm run deploy`. It builds, applies any new migrations to the production database, and deploys.

**From GitHub**, so every push to `main` redeploys. Steps 1 and 2 are already done for grubbl.io:

1. In Cloudflare → DNS for grubbl.io, **delete any existing records named `grubbl.io` (`@`) or `www`** (for example parking records). Custom domains can't be attached while they exist.
2. Create the database once: `npx wrangler d1 create grubblio`, and paste the `database_id` it prints into the `d1_databases` entry in [wrangler.jsonc](wrangler.jsonc).
3. Push the repo to GitHub. In the Cloudflare dashboard, go to **Workers & Pages → Create → Import a repository** and pick it.
4. Set the build settings:
   - **Build command:** `npm run fetch-images -- --restore && npm run build`
   - **Deploy command:** `npx wrangler d1 migrations apply grubblio --remote && npx wrangler deploy`. This applies any new migrations before each deploy.
   - **Build variable:** `PIXABAY_API_KEY`. The build restores the stock photos that aren't committed (see [Photos and sounds](#photos-and-sounds)). Without it, those dishes show their emoji.
5. Commit new Commons photos in `assets/dishes/` along with `credits.json`.

Either way, the Worker needs three **secrets** (`npx wrangler secret put <NAME>`, or the Worker's **Settings → Variables and Secrets**), each a long random string from `openssl rand -base64 32` except the Resend key:

| Secret | Purpose | If missing |
|---|---|---|
| `PUZZLE_SECRET` | Encrypts Rush hour puzzle ids, so the answer can't be read out of them | Falls back to a dev key that's public in this repo |
| `BETTER_AUTH_SECRET` | Signs login sessions | Sign-in fails (anonymous play still works) |
| `RESEND_API_KEY` | Sends login codes ([Resend setup](#setting-up-the-code-emails-resend)) | No code emails, so nobody can sign up |

## How game state is kept

The game itself is replayed, not stored: the client keeps the list of guessed dish ids, and `POST /api/state` rebuilds the board from them each time. The answer is sent only after the game ends.

- **In the browser** (`localStorage`): `grubblio:current` holds the game on screen, `grubblio:daily` the latest Daily dish, and `grubblio:rush` an unfinished Rush hour.
- **On the server**, only for signed-in players: each guess also updates their `plays` row. Game history and the Rush hour rule across devices come from there.
- **Rush hour ids** carry their answer, AES-GCM encrypted ([server/practice.ts](server/practice.ts)), so they survive deploys and need no table of their own.

## Not covered by this prototype (needed for production)

- **Dish data in a database.** Dishes are still in code (`server/dishes.ts`). That's fine while developers edit them; move them to D1 once non-developers need an editor.
- **Reviewing upcoming answers.** Answers are picked on the day, so there's nothing to review ahead of time. A daily Cron Trigger running the `--days` logic would keep a month picked ahead for review.
- **Anti-cheat.** Because games are replayed from the client's guess list, anyone can send invented guesses to reach the reveal. Signed-in history can't be rewritten after a loss, but an answer seen in a private window can still be "guessed" on the account. Server-side game sessions, or signed state tokens, would fix this.
- **Image curation and hosting.** About 100 newer Commons photos were checked by file name only; someone should review every photo by eye. Production should serve them from a CDN. A paid library such as Adobe Stock needs a purchased licence for each image.
- **Content.** Editorial review of ingredient order and difficulty for each answer, and playtesting.
- **Social sign-in** (Google, Apple, Facebook). Better Auth supports them under `socialProviders` in server/auth.ts. Each needs a developer app with that company and a privacy policy page; Apple needs a paid developer account.
- **Bot protection on sign-up.** Code emails are rate-limited per IP, but a captcha such as Cloudflare Turnstile (Better Auth's `captcha` plugin) would stop scripted sign-ups from using up the email quota.
- **Account settings.** Changing name, email or password while signed in, and deleting an account, aren't in the UI yet.
- **Privacy policy.** Needed now that the site stores emails, and required by every social sign-in provider.
